# 나라장터 법령 위반 판정 — 세 원천 앙상블

`/workspace/oh/dacon_o` 와 `/workspace/song/solution` 의 두 접근을 한 파이프라인으로 합친 제출물이다.
**원본 두 폴더는 건드리지 않았다.** `engines/` 에 그 시점의 사본을 두어 대조할 수 있게 했다.

## 합치기 전에 잰 것

두 갈래를 dev 200건에서 같은 채점기로 재보니 이랬다.

| 갈래 | dev Macro F1 |
|---|---:|
| oh — 게이트 + logprob 임계값 | 0.3186 |
| song — 사실추출 + 코드 법령적용 | 0.5752 |
| song 을 **LLM 없이 규칙만으로** 돌린 것 | **0.5756** |

song 은 LLM 을 붙이든 안 붙이든 총점이 같다. 그런데 **항목별로는 전혀 다르다.**

```
        LLM 이 이긴 항목            LLM 이 진 항목
  v3  0.857 → 1.000            v19  0.833 → 0.546
  v5  0.833 → 1.000            v20  0.533 → 0.000
  v7  0.769 → 1.000            v22  0.727 → 0.500
  v15 0.750 → 0.923            v6   0.600 → 0.455
```

총점만 보면 LLM 이 무용해 보이지만, 항목 단위로는 승패가 뚜렷하다.
그래서 이 앙상블은 두 계층이 아니라 **원천 셋**을 다룬다.

| 원천 | 정체 | 추가 LLM 콜 |
|---|---|---:|
| `rule` | A계층을 규칙 사실만으로 판정 | 0 |
| `song` | A계층에 LLM 사실을 융합해 판정 | (A계층 콜에 포함) |
| `oh` | B계층 P(위반) 을 임계값으로 자름 | 그룹 수만큼 |

항목별로 최고를 고르면 dev 0.6672 (오라클 상한). 실제 융합 성적은 아래 **성적** 참고.

## 성적 (dev 200건)

| | Macro F1 |
|---|---:|
| oh 단독 | 0.3186 |
| song 단독 | 0.5752 |
| rule 단독 | 0.5756 |
| **융합 — 적합** | **0.7166** |
| **융합 — 5겹 교차검증** | **0.6388** |

**0.6388 이 판단 기준이다.** 0.7166 은 같은 데이터로 고르고 같은 데이터로 잰 값이라
반드시 낙관적이다. 교차검증은 '항목별로 후보를 고르는 절차 자체'를 겹마다 다시 수행해
검증 폴드에서만 채점한 값이므로, 새 데이터에서 기대할 수 있는 쪽에 가깝다.

기준 원천(song 단독 0.5752) 대비 **+0.064** 다.

확정된 항목별 모드는 이렇다 — `song` 11 · `and` 8 · `oh` 3 · `rule` 2.

```
  v1  oh@0.98              v9   and(song|oh)@0.98    v20  and(rule|oh)@0.30
  v12 oh@0.92              v2   and(rule|song)       v22  and(rule|oh)@0.02
  v24 oh@0.98              v8   and(rule|song)       v6   rule
                           v14  and(rule|song)       v10  rule
                           v18  and(rule|song)
                           v19  and(rule|song)
  나머지 11항목: song
```

`and(rule|song)` 이 8항목에서 채택된 것이 이 앙상블의 핵심이다. 같은 `law.judge` 를
규칙 사실과 LLM 융합 사실로 각각 돌려 **둘 다 위반이라고 할 때만** 위반으로 본다.
`v8` 은 0.833 → 0.909, `v19` 는 0.833 → 0.909, `v2` 는 0.800 → 0.857 로 FP 가 정리됐다.

### 실행 비용

확정 규칙에서 B계층이 쓰는 항목은 `v1·v9·v12·v20·v22·v24` 여섯 개, 그룹은 다섯이다.

| | 레코드당 콜 |
|---|---:|
| A계층 | 1.00 |
| B계층 (확정 규칙) | 4.42 |
| B계층 (`--collect` 수집 모드) | 6.42 |

평가 데이터 1,853건이면 약 **10,000콜**이다. dev 200건 기준 A계층 316초 · B계층 1,483초
(수집 모드 1,285콜)였으므로, 확정 규칙으로는 1,853건에 **대략 2.5~3시간**을 잡아야 한다.
평가 서버 런타임이 빠듯하면 `oh` 채택 항목을 이득이 큰 순(`v22` +0.162 · `v20` +0.217 ·
`v1` +0.420)으로 남기고 나머지를 `song` 으로 되돌려 그룹 수를 줄이면 된다.

## 구조

```
공고 + meta
   │
   ├─ A계층 : 신호추출 ─┬─ LLM 사실 1콜 → fuse → law.judge → song
   │                    └─ (LLM 없이)      rule_facts → law.judge → rule
   │
   ├─ B계층 : 메타 게이트 → 그룹 LLM 콜 → logprob → 확률          → oh
   │
   └─ 융합  : 항목별 {rule | song | oh | or(A,B) | and(A,B)} → submission.csv
```

`rule` 은 `song` 과 같은 `law.judge` 를 규칙 사실로 한 번 더 돌린 것뿐이라 **공짜다.**
`or` 는 재현율을, `and` 는 정밀도를 산다. 지표가 양성 클래스 F1 이라
항목별 양성 희소도에 따라 유리한 쪽이 갈린다.

### 엔진은 하나만 뜬다

두 계층이 각자 `LLM(...)` 을 만들면 26B 모델을 두 번 적재한다.
`SharedEngine` 하나를 만들고 계층별 어댑터(`SongPort`·`OhPort`)로 감싸 공유한다.
`OhPort` 만 `logprobs=20` 을 켠다.

B계층은 **융합규칙이 실제로 쓰는 항목만** 묻는다. 전 항목을 물으면 레코드당 6.5콜이지만,
융합규칙이 고른 항목만 물으면 그보다 훨씬 적다. 실행 로그의 `레코드당_평균콜` 로 확인할 수 있다.

## 실행

```bash
# 모델 없이 흐름·형식 확인 (rule 원천만 동작)
python3 script.py --mock

# dev 채점
python3 script.py --input dev.jsonl.gz --output-dir output/dev
python3 tools/score_dev.py output/dev/submission.csv

# 융합규칙 다시 맞추기 — B계층에 24항목 전부를 물어 원천 셋을 모두 덤프한다
python3 script.py --input dev.jsonl.gz --output-dir output/fit --dump-parts output/fit --collect
python3 tools/fit_fusion.py output/fit --base song --margin 0.05
python3 tools/fit_fusion.py output/fit --base song --margin 0.05 --write

# 제출 ZIP (검사 통과해야 만들어진다)
python3 tools/make_submit.py
```

## 주의

- **`--collect` 는 학습 전용이다.** 제출 실행에 쓰면 B계층 콜이 최대가 된다.
- **융합규칙·임계값을 런타임에 고치지 말 것.** 대회 규칙이 샘플 간 예측 의존을 금지한다.
  테스트셋 분포를 보고 정하는 것은 규칙 위반이다. 오프라인 결과만 JSON 에 반영한다.
- **`model/` 을 제출 ZIP 에서 빼지 말 것.** 자산이 없어도 크래시 없이 돌아가지만
  조문 근거·경쟁제품 조인·융합규칙이 전부 빠진 채 점수만 조용히 떨어진다.
  `tools/make_submit.py` 가 이 누락을 검사해 ZIP 생성을 막는다.
- **`fit_fusion.py` 의 적합 점수를 믿지 말 것.** dev 200건은 항목당 양성이 5~8개다.
  24항목 × 약 250후보에서 최댓값을 고르면 상당수가 잡음이다. **교차검증 값으로 판단한다.**
- 근거문구에 줄바꿈이 들어가는 것은 정상이다. 주최측 `dev_labels.csv` 자체가
  근거셀 54건 중 2건에 줄바꿈을 포함한다. 원문 부분문자열을 그대로 쓰라는 규약 때문이다.
- `--limit` 으로 앞 N건만 돌릴 수 있다. 평가 데이터의 id·건수는 어디에도 하드코딩하지 않는다.

## 규칙 준수

| 규칙 | 이 제출물 |
|---|---|
| 고정 LLM 외 모델 금지 · 파인튜닝 금지 | 학습 절차·가중치 파일 없음. `model/` 은 JSON·CSV·규칙 코드뿐 (130KB) |
| 공고당 고정 LLM 정상 호출 1회 이상 | A계층이 레코드당 1콜. 로그의 `정상응답` 이 건수와 같은지 확인할 것 |
| 외부 LLM·API·네트워크 호출 금지 | 표준 라이브러리만. `make_submit.py` 가 소스를 검사 |
| 샘플 간 예측 의존 금지 | 융합규칙·임계값·게이트 전부 `model/` 의 상수. 런타임 갱신 없음 |
| 평가 데이터 id·건수 하드코딩 금지 | 입력에서 읽어 그대로 출력. 소스에 `PPS-` 문자열 없음 |
| 법령은 배포 스냅샷 기준 | `data/법령패키지/` 만 사용 |
| 제출물 2GB 이하 | 130KB |

`python3 script.py --mock` 을 ZIP 압축 해제본 + `data/` 만 있는 디렉토리에서 돌려
평가 서버 배치(평탄 배치)로 동작하는 것을 확인했다.
